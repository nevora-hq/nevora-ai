# 全記事見直し(企画からの全面書き直し)の手順

- 手順は `作成中/_指示_*.md`・`作成中/_報告_*.md` にその都度断片的にしか残らないため、本ファイルを正本として一本化する。
- **多層判定(`run-local.js`の第1〜6層・self-test)は経ない。** 最終判定は依頼者の目視。理由: run-local.jsのself-testは、再開条件がそろい依頼者が使うと決めるまで使わない(`docs/pipeline/autonomy/SELFTEST-PAUSE.md`の「再開条件」参照)。全記事見直し・ルール改修の期間は、この経路を使わない運用にしている。
- **このサイトに公開ゲートの台帳(`publish-ledger.json`・`ledger-add-visual-check.js`)は無い**(2026-11-20に、`.claude/agents/publisher.md` の「公開できる内容の確認」に合わせて、台帳への記録の手順を削除した)。公開してよい内容かどうかは、publisher.md の「公開前の必須確認」(`verify-article.js` の全ブロッキング項目など)で確かめる。
- 「作成中/」は `サイト運営/記事データ/作成中/`、「公開待ち/」「公開済み/」は `サイト運営/記事データ/` の下を指す。報告・進捗のパスはフルパスで書く。

## 手順

1. **対象の選定**: 書き直す記事の一覧を `作成中/_対象_第N回_YYYY-MM-DD.md` に作る(選定理由・件数を明記)。まだ書き直していない記事から選ぶ。
2. **書き直し**: 対象記事を企画から書き直す(タイトル・見出し・本文・図表・出典等)。ファイル名・`date`・URLは元のまま変えない。1記事の流れと、置き換え前後の確認は、下の「1記事の書き直しの流れと、置き換え前後の確認」のとおり。
3. **push前の項目35確認(2026-09-28追加、再発防止)**: 書き直した記事のうち、図解(`charts`)を新規作成・変更した記事、またはfrontmatter(`heroImage`・`thumbnail`等)を書き換えた記事は、pushする前に必ず対象記事へ `node scripts/verify-rendered-layout.js --strict <slug>` を実行し、検出0件を確認する。0件でない記事は、その記事だけ差し戻して直すか、依頼者に報告して指示を仰ぐ(検出が残ったままpushしない)。図は、置いただけで済ませず、画面で自分の目で確かめる。**`--strict` は幅 320・375・768px で、文字が線・図形・矢印・他の文字に重なると不合格にする。** 余白を多めに取り、文字の下に帯を敷くときは `data-allow-overlap` を付ける(重なる配置そのものが意図的なときだけ。迷ったら付けず相談)。質の悪い図(手抜きの図、他の記事と同じ絵に文字だけ変えた図、何の図か分からない図)を出さない。図の本数の基準は writer.md 規則28(g)が正で、ここでは変えない。
4. **依頼者の目視確認**: 書き直した記事を依頼者が目視し、可否を判断する。依頼者のOKが出る前に、公開済みを上書きしない。OKが出た本数が公開の単位になる。**依頼者がOKした題・導入のフックは固定し、依頼者の許可なく変えない**(OKしていないものは直してよい。前の回の訂正も共通の指示の先頭に書く)。
   - **4-1. 目視用のページ(依頼者が見る回)**: 確定前の下書きを `サイト運営/サイト本体/content/articles/` に、公開済みと衝突しない名前(slug の末尾に `_目視<記号>` を付ける。例: `2026-10-30_xxx_目視A.md`)でコピーして開く。このフォルダは git の追跡外で、`npm run dev` や `npm run build` の前処理(`sync-content.js`)が消すので、目視用は消えても作り直せる。**開発サーバーを起動したあとにコピーする**(起動時の前処理で消えるため)。記事の索引(`node scripts/generate-seo-files.mjs` など)の作り直しが要るなら先に実行する。開発サーバーは、並行して動いている作業があるので、止めない・再起動しない。目視用URLの一覧を `作成中/<回>/目視用URL.md` に置く(各URLの HTTP ステータスと、本文の画像が欠けていないことを取得して確かめた結果つき。確かめていない項目には「確認済み」と書かない。「どこを開く・何を見る・はい/いいえ」の聞き方を付ける)。前回から変えた分は、前回のURLを書き換えず、新しい名前で出す。依頼者が読むもの(URLの一覧・見る場所・はい/いいえの聞き方)は、回のフォルダ(`作成中/<回>/依頼者が見る/`)の1か所に写しを集め、「場所の案内」を1枚作る(元は動かさない。報告にはそのフォルダのフルパスを書く。ファイル名だけを書くと古い資料を開かれる)。目視が終わったら、目視用の写しを消し、開発サーバーを止めてよいかは依頼者に聞く(不在の回は止めない)。**画面写しは親が自分で開いて見る**(担当の報告だけで済ませない。CLAUDE.md)。
5. **commit・push**: 記事データ・画像の変更をcommitし、pushする(commit・pushをしてよいのは、publisher.md の公開の手順を実行する束ねる側だけ)。記事・リンク表示・画像は1つのcommitにまとめ、pushは1回にする。公開前の必須確認(`verify-article.js` の全ブロッキング項目、`thumbnail`・画像パスの `git ls-files` 確認、描画検査)は `.claude/agents/publisher.md` のとおり。依頼者の目視を公開のあとにする回は、公開した記事と、その旨を報告に書く。
6. **push後の確認**: push から最低5分待ち、Vercelのデプロイ成功(トップページ・記事ページHTTP 200、sitemapの記事URL件数の整合)を確認する(CLAUDE.mdのデプロイ運用ルール)。

## 1記事の書き直しの流れと、置き換え前後の確認

**流れ(1記事1体)**
(a)落とさない中身(安全の指示=個人情報・機密を入力しない注意、利用規約・著作権・商用利用の注意、依頼者の方針)を企画書(`meta.md`)に書き写し、構成を設計する。(b)本文を書き直す。(c)部品(図解・要点ボックス・診断など)を整える。(d)画像を置く見出しを、置ける見出しへ移す。(e)通読(新しい担当が全文)。直した文は直す前と並べ、別の新しい担当が前後の文とセットで「文脈読み」する。(f)指摘を文脈で1つずつ見て直し、別の新しい担当が同じ文を再確認する。(g)検査(`verify-article.js`。地の文400字の連続の確認を含む)。(h)回帰チェック(落とさない中身が残るか。新しい担当が全文を読む)。

**置き換え前後の確認(push前)**
- 置き換えは同名ファイルの上書きにし、ファイル名(=slug=URL)と `date` は変えない。公開待ちはキューが付けた後のファイル名を使う(公開時にファイル名の日付が変わってURLが変わった事故がある)。
- **既存の公開済み記事を修正したときは、新記事として公開しない。** 完成後、URL・slug・公開日(`date`)を変えず、最終更新日(`updatedDate`)だけを、実行直前の当日の日付(`"YYYY-MM-DD"`、時刻なし)にして、既存記事として公開する(新記事として公開すると、検索エンジンの評価が伸びるまで時間がかかるため。他サイトの運営者の決定)。同じ検索意図の公開済み記事が既にあるかの判断は、記事を直す担当が行い、判断がつかないときは報告に出す。誤字・表記ゆれだけの空更新はしない。同じ値を何十本にも当てる前に、対象リストの生成根拠をサンプルで確認する(実質の修正でない記事が混入した前例がある)。
- **公開待ちの記事の書き直しには `updatedDate` を付けない**(公開の処理 `queue-release.js` が `date` を公開日に書き換えるため、`updatedDate` の方が前の日付になり、検査の項目に引っかかる)。公開待ちの記事を直したときは、publisher.md の「公開の決まり」のエのとおり。
- 下書きと公開済みの `title`・`date`・導入の最初の1文が一致していること。改行は LF(CR が0行、末尾に改行あり)。
- `thumbnail` と本文の画像パスがすべて git に追跡されていること(`git ls-files` で確かめる)。図の絵柄の索引ファイルが読み込むファイルがすべて追跡されていること(未 commit のファイルを読み込んでビルドが失敗した前例がある)。
- 内部リンク: 全記事から「実在しない `/posts/…`」を列挙して0件にする。
- HTML コメント: `grep -rn "<!--" サイト運営/記事データ/公開済み サイト運営/記事データ/公開待ち` で0件にする(画面に出ない運用メモが本文に残り、ソースに出ていた)。
- 「？」「！」の直後・「。」の直後に絵文字を置いていないこと(writer.md 規則27の運用)。

## まとめて直す回(組ごと)(2026-10-07追加)

多くの記事をまとめて直す回の進め方。上の「手順」の4(依頼者の目視)は、依頼者が不在の回は、本文を直していない担当の判定に置き換える(CLAUDE.md の「依頼者が不在の回」)。公開の手順の正は `.claude/agents/publisher.md`(「公開できる内容の確認」「公開前の必須確認」)で、ここには書き写さない。

1. **20本ずつの組に分ける**。組の中の担当の並べ方は CLAUDE.md の作業方針(基本は20体)。
2. **組ごとに、次の順で行う**: 担当が直す → 検査(`verify-article.js` など。走らせ方は writer.md の「検査の走らせ方」)→ 本文を直していない担当の判定(No がなくなるまで。`docs/pipeline/JUDGE-ITEMS.md`)→ 公開(`publisher.md` の手順。pushは組ごとに1回)→ 本番の確認(push から5分待ち、トップ・記事数・その組の記事を確かめる。記事数が減っていたら、次の組へ進まず原因を直す)。
3. **指示の写しと再開の手順**: 依頼者の1通の全文を `サイト運営/記事データ/作成中/_指示_<回>_<日付>.md` に写す。進捗ファイル `サイト運営/記事データ/作成中/_進捗_<回>_<日付>.md` を作り、先頭に再開の手順(「コンパクトのあと、または再開のときは、_指示_<回>_<日付>.md とこのファイルを読み直し、git status で commit していない変更が無いかを確かめ、下の『次の手順』から、止まらずに続ける。」。依頼者が不在の回は「依頼者は不在。質問しない。」を足す)を置いて消さない。その下に「次の手順」を1行で書き、手順が1つ進むたびに書き直す。
4. **個別の小さな直し**は、組の作業に混ぜず、先に1つの commit で出す。
5. **変えていない記事**は、公開の対象にしない(commit に入れない)。
6. **共通の指示ファイルの必須項目(2026-11-20追加)**。回のフォルダ(`作成中/` の下)に `_共通指示_<回>_<日付>.md` を作り、各担当の起動プロンプトは「そのファイルを最初に読め」と「割り当て1つ」だけにする。共通の指示には次を必ず書く。規則の本文は writer.md が唯一の正で、共通の指示には写さず参照だけを書く。
   1. 日付と、回のフォルダ・サイト本体・記事の置き場のフルパス。
   2. 今回が何をする回か(下書きを作る回/確認する回/調べる回)と、してはいけないこと。公開・置き換え・消去・リンクの付け替え・commit・push・fetch・pull を担当にさせない。git は読み取り(status・diff・log・show)だけ。add・commit・push・checkout・reset・stash・`--no-verify` は使わせない。
   3. 触ってよいもの(自分の担当フォルダの新規ファイル、または指定の記事1本だけ)と、触らないもの(他の担当の下書き、公開済み・公開待ち、規則本文、検査スクリプト、サイトのコード、スキル、`current-rules.json`)。
   4. 変えないもの(②の悩み=記事の問い、題・slug・date、安全の指示、見出しの数と順、既存の図・出典の記法)と、新しい数字・機能名・料金・出典を足さないこと。
   5. 最優先の原則: 悩みをずらさない。安全の指示(個人情報・機密を入力しない、利用規約・著作権の注意など)を弱めない。出典を新しく探しに行かない。数字や機能の断定を作らない。検査を通すためだけの移動をしない。
   6. 直す前の写しを `<元の名前>_<回>前.md` で同じフォルダに残す。直し前後(全文・字数・理由)を `直し前後_<回>.md` に書く。回をまたいだ巻き戻しができるようにする。
   7. 検査の走らせ方: 公開名(`<slug>.md`)の写しを自分専用の一時フォルダに作って走らせ、リポジトリに何も書かない形(標準出力だけ)で、結果を担当フォルダへ出す。書き込みのおそれがある引数は使わない。書き込みのおそれがあれば「未実行」と書く。他の担当の結果を上書きしない。
   8. 改行は LF のまま(CRLF にしない)。
   9. 質問しない。依頼者が在席でも不在でも、最も妥当な読みで進め、読みの内容を報告に書く。決められない点は直さずに一覧にして報告する。
   10. 出力と報告の型: 内容はファイルに書き、完了報告は3行以内の要点だけにする(中身はファイル)。パスはフルパス。事実・推測・未確認を分けて書く。工程ごとに担当フォルダへ保存する(途中で止まっても再開できるように)。
   11. 検査は「必ず直す項目0件」まで直す(`verify-article.js` のブロッキング項目)。ただし、検査を通すためだけの直しはしない(nevora-pipeline-verifier.md の「位置づけ」)。
7. **確認担当の独立性**: **書く担当と確認する担当は別の新しい担当にする。** 書いた担当は自分の記事の確認をしない。確認担当には、書き手の報告(「書き直しの報告」「直し前後」など)を読ませない(説明に引きずられないため)。渡すのは、読んでよいファイルの名前を決めた一覧だけにする(例: 旧版の題とフック・新しい題と導入・本文の最新版の3つ)。他の確認担当の出力・直し前後・対応表は渡さない。確認の結果は1つのファイルに出力させる。確認の手順書は共通の指示と別のファイルにする。観点は次のとおり。
   - **悩みのずれ**〔悩み型・問い型〕: 旧版の題と導入から「読者の悩み」を1文で書き、新しい題・導入・本文から同じことを書いて、「同じ/ずれた/迷う」を判定する。情報型は、代わりに「題が約束した事実(何が・いつ・誰が)が本文に残っているか」を見る。
   - **規則違反**: 該当する規則の番号ごとに、違反の文を引用して書く(引用は逐語。要約を引用の形にしない。CONTRIBUTING 30-5)。
   - **文脈読み**: 前後2文つきで1文ずつ読み、「やや不自然/不自然」だけを、場所(見出し+文頭15字)・分類・理由・優先度(高=読者が意味を取り違える・つまずく/中=読みにくい/低=好み)・直し案1文で出す。
   - **回帰チェック**: 企画書の「落とさない中身」と安全の指示が本文に残っているか。
   同じ記事を直したあとは、直した箇所について、別の新しい担当が再確認する。「直したあとの再確認が無い」記事は完了にしない(未完として報告する)。
8. **巡数と終わり方(数は参考で、止める条件は(ii)〜(vii)の0件・一致だけ)**。1記事の標準は、書く1体→確認→直す。回ごとに巡数の上限を決めて共通の指示に書く(上限を決めないと終わらない。例: 直しは最大2巡、再確認は1巡)。終わり方は着手の前に定義する。完了(目視待ち)は次のすべてを満たしたときとする。(i)〔悩み型・問い型〕悩みが、新しい2体の独立した判定で「同じ」。(ii)規則違反が0(新しい2体)。(iii)文脈読みで「高」と、直せる「中」が0。(iv)題・URL・date が旧版と一致。(v)検査(`verify-article.js`)の悪化なし。(vi)プレビューのページが開く(HTTP 200)・画像欠け0・直した文が入っている。(vii)判断が要る点は「依頼者が決める点」の表に載っている。区分は、完了(目視待ち)/指摘付きで目視可(巡数の上限に達し高・中が残るが目視はできる)/中止(悪化が戻せない)の3つ。区分ごとの理由を `完了判定_<回>.md` に書く。確認の体数が定義より少なかった場合(起動し忘れなど)は、弱めた点として判定に正直に書く。
9. **並列で起動するときの運用**: 依頼者が「並列」と書いたときは、実際に並列で起動する(「未確認だから直列」にしない)。段階を踏むなら、最初の3〜4体で型を確かめ、問題なければ全体数にする。1記事を1体に割り当てる。起動する担当は番号つきの一覧にして共通の指示に載せ、判定には「定義した体数」と「実際に起動した体数」を並べて書く(起動し忘れを見つけるため。違えば弱めた点として書く)。20体は同時に起動する数の目安で、環境に同時実行の上限があれば、その上限で頭打ちになる。ブラウザを操作する担当(voice-researcher)は、同時に5体までとし、同じドメインへの連続の読み込みは数秒あける。
10. **依頼者の目視で「No のまま通す」項目を決めるとき**は、通す項目と理由を `_指示_<回>_<日付>.md` に原文のまま記録する。ライターは、検査を通すために部品を足さない。

## 調べの回の進め方(2026-11-20追加)

1. 1回に当てる規則(または観点)は1つにする。複数を一度に当てると、どの直しが改善か分からなくなる。全記事ではなく10〜13本に当てて、別の新しい担当が確認する。
2. 実行(公開・置き換え・消去)と調べ(読むだけ)を分ける。調べの回は報告の先頭に「何も実行していない」と書く。
3. 依頼者の1通は、始める前に `_指示_<回>_<日付>.md` へ全文を写す。進捗ファイルを作り、先頭に再開の手順を置く(まとめて直す回の項目3と同じ)。
4. 依頼者の発言は、決定台帳(`作成中/運営者の決定_台帳.md`。未作成。依頼者の発言が規則を決めた回に作る)に原文のまま追記し、設計役の整理(依頼者の発言に無い案)は別の層に分けて書く。決定は更新して1つにし、積み上げない。
5. 規則の変更は、台帳の決定に結びつくものだけ。判定の合否が変わる変更は、報告の最初に変更前後の挙動を書く。
6. 確認は、依頼者の目視を最終判定にし、機械検査(`verify-article.js`・`verify-rendered-layout.js --strict`)は「悪化していないか」を見る役にする。
7. 報告は、事実(読んで確かめた)/推測(読みからの判断)/未確認(読んでいない)に分ける。「確認済み」と書くのは、取得して確かめた項目だけ。報告前に「実在の確認」の表(ファイル・実在・サイズ・フルパス)を作り、`output-crosscheck` で突き合わせる(報告に「ある」と書いたファイルが無かった事故があった)。

作業の成果物なので `サイト運営/記事データ/作成中/<回ごとのフォルダ>/` に置き、docs には置かない。運営者の発言を含まない記録と明記する。
- H2字数の記録: 記事ごと・H2ごとの地の文の字数と文数。通読で「内容が足りているか」を判断する手がかりにするためで、字数を満たすための水増しはしない。
- 回帰チェック: 書き直した記事ごとに、本文を直していない担当が全文を読み、企画書の「落とさない中身」の各項目と安全の指示が本文に残っているかを確かめた表。2体以上が「無い」とした項目は最小の修正で戻す。
- 言い回しの出現数: 同じ言い回し(例:「ではないでしょうか」「〜がおすすめです」)の本文全体・最初のH2での出現数。語尾の乱用を数字で示す(合否にしない)。
- 引用表: 検査項目について、規則・手順・コードのコメントの該当記載を「ファイル:行:その文」で並べ、文書どうしの食い違いを別の担当が見つけられるようにする。検査項目とJUDGE-ITEMSの番号体系が別であることを先頭に書く。
