# 似た記事の集約(吸収)と消去の手順

作成: 2026-11-20。他サイトで確定した手順を、AI活用ジャンルに読み替えて置いたもの。記事数が増えたときの手順書である。

## 実行の条件(最初に読む)

**この手順は、運営者(依頼者)が決めるまで実行しない。** 公開済みは約40本で、いま集約が必要かどうかも、運営者が決める。次の点は、他サイトの運営者も明示の決定をしていない(未決)。このサイトで実行するときは、作業の前に運営者へ確認する(依頼者が不在の回は、実行せず、この手順を使わない。洗い出し〔読むだけ〕までは行ってよい)。

1. **消去の方式**: 吸収される記事のファイルを消すか、`非公開アーカイブ/` へ移すか。旧URLを転送(301)するか、404のままにするか。
2. **転送(301)の置き場**: このサイトは完全静的エクスポートなので、転送を足すなら `vercel.json` の redirects(`next.config.js` の redirects は効かない)。`vercel.json` はいま無く、作る場合は新規ファイルになる。
3. 公開待ち・依頼者がOKしたフックの記事が、吸収先または吸収される側になるとき。
4. 分けた問い(下の「集約するか、問いを分けるか」の(b))の声が取れないとき。
5. 作業記録(作成中のフォルダ・進捗)に消す記事の名前が残る扱い。
6. 「と思います」「でしょう」「かもしれません」の使い分けの許容範囲(取り込むときの文の書き方)。
7. 地の文の長さ。**字数の下限・上限は置かない**(writer.md 規則33(c)。字数は報告に書くだけで、合否に使わない)。

このサイトに公開ゲートの台帳は無い(`.claude/agents/publisher.md`)ので、台帳のエントリを消す・残すという論点は無い。

## 目的

同じ検索意図の記事が複数あると、検索エンジンが似た記事と見なし、インデックスされなくなる。似た記事を1本に集約(吸収)し、1本あたりの内容を厚くする。記事数は目的ではなく結果である。

## 方針(運営者の決定を読み替えたもの)

1. 質が低すぎる記事や、内容が重複する記事があるときは、**3本の似た記事を3本に書き直して、ほとんど同じ記事にすることは絶対に避ける。** 似た記事は、集約(吸収)して1本にしてよい。
2. 後から直す記事が、以前に直した記事と同じ悩み(検索意図)に答えているときは、書き直さず、以前の完成版に集約する。吸収される記事が答えていて吸収先がまだ答えていない要素だけを加える。
3. 吸収されて無くなる記事は、サイトの現在の状態から消す(検索・ホーム・一覧のリンクと表示情報も消す)。これまでの評価は引き継がない。
4. 同じ悩みの記事が複数あるときは、(a)集約するか、(b)基本の構成・悩みの種類・解決法をはっきり分けるか(分けることが難しい記事は集約)を決める。(b)のとき、分けた各記事の悩みは、規則34のとおり実在の声から出す(悩み型でない記事は、問い・知りたいことを分ける)。
5. **無理に1本に混ぜない。** 悩みが別の記事は、統合せずに残すか、質が低ければ削除する。サイト内のリンク切れは絶対に出さない(消す記事を指す他の記事のリンクを付け替える)。
6. **「似ている」は、話題が同じことではなく、同じ主要な悩み(検索意図)に答える記事のこと**と読む(設計役の整理。運営者の発言にこの定義は無い)。例: 「ChatGPT 無料版の使い方」と「ChatGPT 有料版の選び方」は、悩みが違えば組にしない。似ているかの判断は、今のサイトにある記事どうしの比較だけで行い、集約の履歴には頼らない。
7. 情報型(AI最新ニュース・新機能)の記事は、「同じ検索意図」でなく「同じ発表・同じ機能」で比べる。古い版の発表を新しい版に集約するのでなく、更新する(`updatedDate`)か、古さが問題になる記事は `非公開アーカイブ/` へ移す。

## 洗い出し

1. 公開済み・公開待ち・直し中の記事どうしを、今のサイトの題・見出し・本文で比べる。
2. 判定は、前の判定を見ていない新しい2体が、互いの結果を見ずに独立に行う。**2体が一致した組だけを同じグループにする。** 割れたものは「新規扱い」、迷うものは「要判断」とし、理由を書く。本文を読んで確かめた組と、題・見出しだけで読んだ組を分けて書く。記事数が少ないうちは、1人の目視に置き換えてよい。
3. 記事数が多いときは、分野ごとに担当に割り当て、全記事の題・概要・読者・タグ・要点・見出し・字数を1つにまとめた一覧(digest)と、題・見出しの2文字の近さの機械類似度、記事→リンク先・記事→被リンク元の表を機械で作って渡す。担当は、グループ名/含まれる記事/各記事の概要と重なり具合(ほぼ同じ内容・一部重複・切り口だけ違う)/統合先として最適な記事とその理由/取り込む価値のある内容/質の優劣、を書く。
4. 結果は `作成中/<回>/` に保存する(`docs/` には置かない)。

**質の判断**(AI が質の良し悪しを決めない。依頼者が決める): ア 真の悩みか。イ 真に悩みを解決しているか。ウ 読者が求める内容か。「かもしれません」が多いのは問題にしない。悪いのは、決めつけ(「〜と思います」)、だらだらした列挙、地の文にした箇条書きの列挙。語尾の数・字数・形式の指標だけで「質が低い」と決めない。

## 集約するか、問いを分けるか

グループごとに、依頼者が(a)集約するか(b)問いを分けるかを決める。(a)のときの残す1本(吸収先)も依頼者が決める。**決まるまで、そのグループは書き直しにも消去にも進まない。** 3本を3本に直して重複の多い同じような記事を残すことは避ける。分けにくければ集約する。依頼者が不在の回は、依頼者の目視が要るグループだけ保留し、残りは洗い出しまでで止める(消去は、方式が未決の間は行わない)。

## 吸収の手順

1. 吸収先に足すのは、吸収される記事が答えていて、吸収先がまだ答えていない分だけ。同じ悩みの分は足さない(追記で積み上げない)。
2. 吸収先は規則どおりに作り直す。URL・slug・`date` は変えず、`updatedDate` だけ実行直前に当日にする。吸収した本数は記事に残さない。

**取り込みのルール(統合を担当する1体への指示。1組1体)**
- 編集してよいのは、統合先の記事1本と自分の報告ファイルだけ。統合元・他の記事・サイトのコードは変えない。移動・削除・commit・push もしない(親が行う)。
- 作業前に統合先と統合元の全文を読む(一覧だけで済ませない)。統合先の本文を先に読み、同じ内容がすでにあれば取り込まない。
- 出典は出典欄(frontmatter の `sources`)だけを扱う。取り込む文に出典の注記があれば、統合元の該当項目を統合先の `sources` に足す(同じURLがあれば足さない)。出典を新しく探しに行かない。出典が無いことを理由に本文を削除・縮小・書き換えしない。
- 安全の注意(個人情報・機密の入力、著作権・商用利用・利用規約、料金・仕様が変わる点の「公式で確かめる」注意)・断定を避ける表現・免責は残す。統合元の⚠️の箱は、統合先に同じ内容が無ければ箱のまま取り込む。表現を強めない。
- 既存の規則・検査にすべて通す。「〜と思います」「〜人も多いと思います」を新しく書かない(事実として書くか、可能性の形にする)。読点でだらだら列挙しない。地の文が400字を超えて続かないようにする。同じ文面の使い回しを作らない。一人称の体験談・伝聞・断定的な効果の約束(B5ルール)を書かない。
- 統合先の題・説明文・tags・summaryPoints・targetReader を、取り込んだ悩みが入る形に更新する。題は題名の決まり(writer.md 規則30)に従う。
- 既存の見出し(H2/H3)の文言は変えない(`charts`・`accordions`・`imageBrief` が見出し文で位置を指す)。新しい節は新しい見出しで足す。統合元の図・画像は持ち込まない。
- 統合先にある内部リンクは残す。統合元を指すリンクは書かない(親が付け替える)。
- 報告の型: ①統合先・統合元 ②題・説明文などの更新 ③字数(変更前・統合元・変更後。報告するだけで合否に使わない) ④取り込んだ内容と取り込まなかった内容(理由つき) ⑤**語の数え**(個人情報・機密・著作権・利用規約・商用利用・有料プラン・公式で確かめる、の件数の前→後。減っていないこと。数は参考で、合否に使わない) ⑥検査結果 ⑦出典欄の変更 ⑧統合元を指すリンク ⑨迷い。

## 親の作業(1組ごと。方式の決定のあと)

1. 統合元を `公開済み/` から、決まった方式(消去または `非公開アーカイブ/` へ移す)で外す。履歴は git に残る。
2. 統合元を指していた他記事のリンクを、統合先へ付け替える(リンク先 slug と案内の文言を統合先の題に合わせる。文言は付け替え先の現在の題にそろえる。同じ文・同じ一覧に付け替え先へのリンクがすでにあるときは、付け替えず外す)。**この付け替えは、CONTRIBUTING 34節(内部リンク絶対保護)の例外として行う**(消す記事へのリンクを残すとリンク切れになるため)。詳しい確認は `.claude/agents/publisher.md` の「記事を取り下げる・題や slug を変えるときの確認」。
3. 題を変えた記事を指すリンク文を、新しい題に更新する(題を変えたら、その題を指すリンク文を全記事から検索して直す)。
4. 統合元の専用画像は、他の記事と共有されないこと(`git grep` で pages・lib・components・styles から参照が無いこと)を確かめてから、消すか残すかを決める(依頼者が決める)。
5. コード内の slug の直書きを `git grep -n "<slug>" -- pages lib components` で確かめる。当たれば、消去の前に依頼者へ報告する。
6. 消去の確認表(記事1本を消すとき手で直す場所と自動で消える場所): 公開済みの記事ファイル=手で外す。`content/` 以下・検索の索引・sitemap・ホーム・カテゴリ・関連記事・次の記事=次のビルドで自動で消える。`public/images/articles/` の専用画像=手で消す(消すか残すかは依頼者が決める)。他記事の内部リンク=自動では直らない(消す前に slug で全記事を検索し、消した後に「実在しない `/posts/…`」を全記事から列挙して0件を確かめる)。
7. 「使われなくなった悩みの記録」(`サイト運営/記事データ/作成中/<回>/使われなくなった悩みの記録.md`): 統合で記事として使われなくなる悩みを、(1)完全に使われなくなった悩み(削除)(2)他の記事の節として残る悩み(統合)に分け、元の記事・扱っていた切り口・理由・吸収先・再度書くなら強めるべき点を書く。次回以降の企画の参考にする。
8. 旧URLの扱い(301の転送をするか、404のままにするか)は、集約の回ごとに依頼者が決める。サイト内のリンク切れは出さない。
9. 公開待ちの記事を指すリンクを張るときは、公開される順が逆にならないか確かめる(`npm run queue:status`。公開待ちの slug は公開で日付が付け替わる)。
10. 本番(push の5分後): トップ200・sitemap の記事URL件数が消した本数だけ減る・吸収先の記事ページ200・消した記事のURLが開けない(404)・サイト内検索とホームの一覧に出ない。

**集約の効果の見方(任意)**: Search Console の「クロール済み - インデックス未登録」の件数を、集約の動機と効果測定に使う(基準日つきで週次に追う)。

**集約で気をつけた失敗**: 統合で安全の注意が落ちる(語の数えで防ぐ)/内部リンクが切れる/題を変えたのにリンク文が旧題のまま/統合後の地の文が400字を超える(文章を変えず、要点ボックスなどで分ける)。
