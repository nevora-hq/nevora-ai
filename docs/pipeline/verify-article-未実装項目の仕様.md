## B. 項目ごとの仕様

### 項目37 内部リンクの文言と遷移先の不一致(止める。JUDGE-ITEMS での扱いはイ)
- 検出: 本文と frontmatter の全文字列の内部リンク `[文言](/パス)` のうち、文言が「特定の記事を指す表現」(末尾が `の選び方`・`とは`・`の違い`・`の使い方`・`のやり方`・`の方法`・`の手順`・`の目安`・`の注意点`・`比較`・`ランキング`・`おすすめ`・`早見表`。足す語は運営者の指示があるものだけ)で、遷移先が `/category/…`・`/tag/…`・`/`(トップ)・記事でないページ・実在しない `/posts/<slug>`(公開済み・公開待ちのファイル名から日付と `.md` を除いて照合)のとき違反。`#`・`?` 以降は切る。出力は違反リンクごとに行・文言・遷移先・分類。
- 根拠: 他サイトで、文言「〜の選び方」の遷移先がカテゴリ一覧だった事故。

### 項目38 本文の箇条書きと summaryPoints のほぼ同文(参考)

## F. verify 以外の未実装の仕組みの仕様(依頼者が決めたときだけ実装。コードは書いていない)

### F-1 本番確認の取得スクリプト `scripts/check-production.js`
- 引数: 本番のトップURL、期待する記事URL件数、確認する記事の slug を空白区切りで複数。
- 取得するもの: トップページの HTTP ステータス / sitemap.xml 内の記事URL(`/posts/` を含む loc)の件数 / 指定した slug の記事ページの HTTP ステータス。件数の数え方は、`generate-seo-files.mjs` が作る sitemap の実物に合わせる。
- 出力: 項目ごとに「取得した URL・HTTP ステータス・件数・取得した時刻(JST)」を1行ずつ。期待件数と実件数が違えば終了コード1。画面の見え方は判定しない(出力の末尾に「画面の見え方は取得では確かめていない」と固定で書く)。出力をそのまま報告の「確認済み」の欄に貼る。
- push から5分待つ決まりは、スクリプトの外(束ねる側)の手順のまま。スクリプトは待たない。`buildId` の取得は任意の参考表示とし、合否に使わない(CLAUDE.md のとおり、スクリプト・docs だけの push では変わらないのが正常)。

### F-2 関連記事・「次の記事」を言葉の近さで選ぶ
現状は `getNextPost` が同カテゴリの日付順(カテゴリは12種と粗く、同じカテゴリでも話題が離れる)。記事数が少ないうちは優先度を下げてよい。
- `lib/posts.js` に `getRelatedPosts(slug)` を新設し、`getNextPost(slug)` を同じ仕組みに置き換える。各記事の「題名・概要・タグ・要点・読者像(あれば)」を連結し、2文字の並び(bigram)に分け、出現する記事が少ない2文字ほど重く見る重みづけ(TF-IDF 風)でコサイン類似度を出す。
- しきい値(初期値 0.08)は、記事数・ジャンルの広さで調整する値であり、合否の基準ではない(他サイトの約200本規模での値で、このサイトでは未検証)。届かない記事は、同じカテゴリでも関連記事に含めない。補助点は、悩みタグ(`worry`)の一致に +0.05、同カテゴリに +0.03。
- 1位を「次の記事」、2位以降を「関連記事」(3件)とする。近い記事が足りないときは同カテゴリの新しい記事で補う(基準に届いた記事が常に先)。frontmatter に任意の `relatedSlugs`(配列)を足し、書かれた slug を先頭に並べる(存在しない・自分自身・「次の記事」と同じものは除く)。
- 確認: 関連記事3件と「次の記事」が出る/欄が空にならない/被リンク0本の記事がどこかから辿れる/本番の記事ページの表示(画面写しは親が自分で開いて見る)。

### F-3 pre-push フック `.githooks/pre-push`
- 有効にする手順: リポジトリのルートで `git config core.hooksPath .githooks`(クローンし直し・PCを替えたとき1回。フックは飛ばさない=`--no-verify` を使わない)。
- 走らせるもの(案): push に含まれる commit の差分のうち `サイト運営/記事データ/公開済み/` と `公開待ち/` の .md に `node scripts/verify-article.js` を実行し、ブロッキング項目が1つでも No なら push を止める。`lib/posts.js` の差分があれば `npm run verify:rendered` も走らせる。参考項目の No と、公開キュー(publish-queue.yml)の自動 commit は対象外。
- 注意: 走らせるのは作業ツリーの状態なので、未 commit の変更があるとそれを含めて確かめる。所要時間が長い(数分)ときは、push を timeout 600000 かバックグラウンドで実行する。他の PC では core.hooksPath の設定が要る点を README に書く。
