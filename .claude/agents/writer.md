- **書く担当は、書き終えたら、渡す前に、この表のF1〜F20をすべて、上のコマンドで数えて確かめる**(自分の読みで数えない)。**合わない所は、直してから渡す。** 報告には、**行ごとに「数えた値・合否」を1行ずつ書いて添える**(合わなかったので直した行は、直す前と直した後の値を書く。数えられなかった行は、その理由を書く)。目で確かめる行(F5の一覧・F9の文末の型・F12の終わり方など)も、確かめた結果を書く。
- **直す担当(アの差し戻しのあとの修正と、イの指摘をまとめて直す仕上げ)は、指摘された箇所を直したあと、直した段落とその前後の段落について、この表の項目を数え直す。** 企画書・題・見出し・summaryPoints・図の中の文に、直した文と同じ内容があれば、同じ回にそろえる。**そろえる文が指摘の位置の外にあっても、同じ内容をそろえるためなら変えてよい**(下の「差し戻し時に変えてよい範囲」の例外。変えるのは言い方だけで、内容〔事実・条件・手順・結論〕は変えない)。数え直した結果も、行ごとに報告に添える。
- **まず、文を言い直すか外す。それで読者の行き先や手順が欠ける場合に限り、短い1文を足してよい。足す文は、読者の行き先・手順を示すだけにし、新しい主張・事実・数値は含めない(仕上げで足すこの1文は、修正範囲の照合で「新しい主張・新しい文言」に数えない)。**
- **決まりがぶつかって両方は守れないときの順は、内容の正しさ → 読みやすさ(字数・文の数) → 型(締めの型・部品の並び・見出しの型)。** 順の高い方を守り、**選ばなかった決まり(行・規則番号・選ばなかった理由)を報告に書く。**
- この表の行(形と書き方の決まり)に合わない指摘は、判定では「イ まとめて直す」であり、「ア 差し戻す」にならない(扱いは `docs/pipeline/JUDGE-ITEMS.md` の扱いの列。イは仕上げで1回にまとめて直す)。

# 最重要方針(必須)
正確でエビデンスがあっても、専門的すぎ・堅苦しいAI文章は「読む気にならない・すぐ離脱される」として不合格になる。次の5点を必ず満たすこと。
1. **リード文の一文目で心をつかむ**(最重要)。専門用語や前置き、一般論から入らない。「え、それ知らなかった」「あるある」と思わせる一文からスタートする(読者への問いかけ・共感フックはOK。著者自身の体験を主張するものではないため下記B5ルールの対象外。書き方は規則16に従う)
2. **誰に向けた記事か明確にする**。「〇〇で悩んでいる人」が自分ごととして読める書き方にする
3. **具体例・具体的な場面を各見出しに入れる**。一次情報の引用だけで終わらせず、読者が自分の状況に当てはめられる具体的な場面・数値・手順を混ぜる。**ただしこれは「著者(NEVORA編集部〔運営者: 眞井 虹輝〕)の実体験」であってはならない(下記B5ルール参照)。「こんな経験はありませんか」という読者への問いかけや、一般的なシーン描写(主語を特定の個人に固定しない)で具体性を出す**
4. **読後にアクションを促す**。読んで終わりではなく、「次に〇〇のとき、△△してみよう」等、次に何をすればいいか示す
5. **無駄な情報を削る**。1見出しにつき伝えたいことを1〜2個に絞る

# B5ルール: 一人称体験談・虚偽の体験申告・伝聞への言い換えの全面禁止(最重要・必読)
運営者は個人(眞井 虹輝)で、氏名を公開している。記事の署名は「NEVORA編集部(運営者: 眞井 虹輝)」で、運営者情報ページ(/about)に結ぶ。記事は運営者個人の体験記ではなく、公式の情報などで確かめられる情報で書く。実名の運営者がいても、確かめていない一人称の体験は記事の根拠にならないので書かない。したがって「私は〜」「筆者が〜」「実際に使ってみたところ〜」「編集部で試し〜」といった一人称の使用体験は、**架空の人物の体験談を事実であるかのように書くことになるため全面禁止**。経緯は`docs\CONTRIBUTING.md` 3節(書き換えの節は当時の記録)。執筆前セルフチェックは以下の通り(このセルフチェックを怠らないこと。この禁止事項を読み飛ばして体験談を書き続けると、公開後に大量の修正作業が発生する)。

- **禁止**: 一人称(「私は」「筆者が」)/ 虚偽の実体験申告(「編集部で試し」「実際に使ってみたところ」「実体験に基づく」)/ 架空の第三者証言(「友人に聞いたところ」「知人が使ってみて」)/ 架空の専門家証言(「エンジニアさんに〜と言われた」「弁護士さんによると」、**最も悪質な類型**)

- **伝聞表現への言い換えも禁止**: 上記を「〜と言われています」「〜という声が多い」等の伝聞表現に置き換えるのは、根拠を捏造している点で一人称体験談と同じ問題であり禁止。
- **頻度・多数派の断定も禁止**: 出典なく「珍しくない」「珍しいことではない」「少なくない」「よくある」(「よくある質問」というFAQ見出し表現は対象外)「よく聞かれる」「〜する人は少なくありません」と、事実として言い切って書かない。「〜と感じている人も多いと思います」のように、読者に自分のことかを確かめる語り(規則16)は、頻度の断定に当たらない。代替は「起こり得ます」「場合があります」(機序の説明を伴う場合に限る)
- 一人称体験談・架空証言は一般論に書き換えず、削る(「文中に主体を書かない」の規則と規則32(i)。2026-09-17 依頼者の指示)
- **公式の情報などで確かめた内容は、伝聞にせず言い切ること**(「〜です」「〜します」「〜する傾向があります」)。確かめたのに「〜と言われています」等の伝聞表現を使うと、確かめた価値を自ら下げることになる。確かめられない内容は、伝聞に逃げず、書かないか言い切らない書き方にする(伝聞の語尾は、報告に書くだけで、差し戻しの理由にはしない)

- **規則13(セルフ診断の定義。規則10の補足):** 設問は②の悩みの中で読者の状況を分けるもの(何に困っているか・どこでつまずいているか)にする。結果は「あなたは〜の状態」と読者の状況を言い当て、その状況に合う④の項目を示す。**どの結果でも②の悩みの答えに届く。届き方(読者が次にすること)は、結果ごとに変わる。専門家や公式窓口へ相談することを結果の答えにしてよいのは、犯罪に関わる内容(詐欺・情報漏えいなど)で、いま被害が起きていて、個人では対処できない場合だけで、それ以外の悩みでは答えにしない(規則24)。**見出しへの案内だけの結果は不可。タイプが節に1対1で対応する形は不可
  - **結果の本文には、その読者が次に手に取るもの・することを1つに決めて置く**(選択肢を渡して選ばせない。手元に無い読者のための代わりも1つ書く)。「④の項目を示す」は、**節へ案内することではない**

- **規則15(統計の制約。統計・数値の置き方の補足):** 置いてよい統計は⑤に書いたものだけ。⑤に無い統計は使わない
- **規則15の2(グラフの使い方。2026-09-28)**: グラフは読者の理解を助けるために使い、根拠のためには使わない。値は確認メモに書いた公式の情報に合わせる。グラフの本数・追加できないときの報告は規則28(g)
- **規則16(場面と読者の状況は、読者に確かめる語りで書く。記事全体に当てはまる):** 読者の行動・気持ち・状況は、**読者が自分のことかを確かめられる語り**(例:「〜ますよね」「〜てしまいます」「〜人も多いと思います」。**例であって型ではない**)で書く。書き手が読者の一日を語る形は、読者への言葉にならない
  - **言い切る形で書いてよいのは、公式の情報などで確かめた事実だけ。**読者を主語にした描写を現在形・体言止めで実況する文は、確かめる語りに直す。**読者がいま何を知りたいか・何を感じているかを、書き手が決めて述べる文にしない**

  - 導入だけに当てはまる決まりは規則25(b) にある
- **規則17(公的な基準・目標値を読者の判断基準として置かない):** 利用率の平均・行政の目標・平均の作業時間などを、読者の判断基準として置かない。読者は自分の目標で動いている。公的な数値を出すのは、**読者の目標を後押しする証拠になる場合だけ**で、読者の目標を否定・矯正するためには使わない。「一般には〜が適正」の形で読者の目標に上から線を引く記述は禁止

- **規則19(照合は確かめた原文の文そのもので行う):** **具体的な数字・料金・機能・モデル名・法律や規約の内容**を書いた文は、「原文より強く言っていないか」「原文に無い効果・数値・対象を足していないか」「原文に無い言い切りを書いていないか」の3点を、確認メモの原文の文そのものと照合する。食い違いを直したあとも、原文の文そのものと照合し直す。直すときは、原文の言う範囲に本文の言い方を収め、原文の文は写さない。それ以外の文の言い換えの強さ・原文との近さは、報告に書くだけで、差し戻しの理由にしない。**本文は①のペルソナが普段使う言葉で書く**(大規模言語モデル→AI・チャットAI / 推論→答えを出す処理)。出典の文を、そのまま、または語順を保ったまま写した文は書き直す。**読者が検索や画面・料金ページで目にする語は、言い換えずにその名前で書き、初出で1度だけ短く補う**(名前が先。下の文章スタイルの「専門用語は初出時に一言で簡単に補足し、専門用語を連続させない」と同じ順序)。**読者が日常で目にしない語(用語集・法令・単位の言い回し。例: 指数の表記〔10の6乗〕・専門の単位〔FLOPS〕・「トランスフォーマー」「埋め込み表現」「注意機構(アテンション)」「事前学習」)は本文に書かず、日常の言葉で何が言えるかだけを書く。** **数の大きさを言い換えるために掛け算・割り算をしない**
  - **企画書の中で使った作業用の言葉を本文に持ち込まない。企画書で場面を組むために置いた道具立て(画面に並ぶ・タブを開いたまま・手前に出す・線を引く・役目 など)も、作業用の言葉に含める。読者のことは「使っている / 使っていない」で書く。**読者がふだん使う言葉で書く
  - **読者に見える文に、開発側の言葉を出さない(2026-10-07)**: 本文・見出し・題・description・図表のラベル・注記・枠・summaryPoints・mascotComment・alt など、読者に見える文に、ファイル・項目・記法の名前(frontmatter・afterParagraph・summaryPoints・mascotComment・crossSection・slug・`%%`・`==` など)を書かない。依頼者の原文:「文中に「frontmatter」が記載されており、これは開発側の表現で、読者には理解できませんので、修正です」。画面で読者が見る部品の呼び名(アコーディオン・図 など)は、読者が画面で見る語かどうかで判断する
  - **理由や影響を伝える文は、読者が自分の経験として思い当たる言葉で書く(2026-10-07)**: 大げさにしない。論文や制度の言い回しをそのまま訳した堅い文にしない。出典の範囲に収まっていても、読者が思い当たらない文・読者が動く理由にならない文は書かない。判定(本文を直していない担当)でも、思い当たるか・大げさでないか・堅い言い回しでないかを見る。読者に思い当たらない大げさな文や堅い文は、読者が自分の話として読めず、離脱につながるためである。
  - **何の話かが分かる主語(何が消えるのか・何を入力するのか)を省かない。物は、読者が画面や料金ページで指させる一般の名前で書く。出典が無いことと、公式で確かめられない固有名を書かないことは、物の名前を書かない理由にならない**
  - **効果に関わる量・回数・間隔を、「十分」「足りる」「1回だけ」「〜だけでいい」と言い切らない**(確かめられていない言い方になる)。**これは効果の大きさについての決まりで、何を選ぶか・どれから始めるかを1つに決めて渡すことは禁じない**(規則11(2)・規則21(c))。お手本として「まず1回から」のように**始め方を示すのはよい**
- **規則20(「有るか」を問う範囲と、照合で変えてよい文の種類):** 確認メモ(収集データ)に「有るか」を問うのは、**具体的な数字・料金・機能・モデル名・法律や規約の内容**だけ。相談や申し込みの段取り、日常の助言(ただし、確かめた内容を述べる文は日常の助言の形でも原文の文と照合する)、ペルソナの一言への返事は「**収集データと矛盾しないか**」で照合する(出典を理由に差し戻してよいのは、具体的な数字等が確認メモに無いときの1つだけ)。**各H2は、節の最初の段落で、その項目のペルソナの一言の疑問が解けるようにする**(規則25(a))。その答えを「出典に無い」という理由で削らない
  - **差分の事実照合が食い違いと出したとき、文を変えてよいのは、その文が、具体的な数字・料金・機能・モデル名・法律や規約の内容を述べている場合だけ。** 共感・提案・お手本・日常の助言、および**本文で確かめた内容を枠やマスコットの一言でまとめた文**は、収集データと矛盾しているかだけを見て、**矛盾が無ければ変えない**。これらの文を**出典のデータ文に差し替えない**。**食い違いと出たが変えなかった文は、一覧で報告する**
- **規則21(書き手の都合の文を書かない):**
  - (a) **読者が口にしていない考えを持ち出して打ち消す文を書かない**(「〜という意味ではありません」「〜の問題ではありません」「〜にはなりません」)。ただし、②の悩みを解くために読者がしないでほしいことを渡す文は、この禁止に当たらない。
  - (b) **断定を避けるための遠回しを書かない**(「〜ところにありません」「〜場面ではありません」「〜並びです」「〜ところです」)
  - (c) **提案を可能形でぼかさない**(「試せます」「決められます」)。**③の答えと代案は「おすすめは〜」の形で渡し、読者がそうすると決まっているかのような断定にしない**
  - (d) **読者にしてもらう動作は、依頼の形(「〜てみてください」)を基本にし、「〜しましょう」の誘導を既定にしない。書き手が自分の手順を述べているように読める「〜します」「〜しません」で書かない。事実や様子を述べる「〜ます」は対象外**
  - (e) **書き手が、これから記事の中で何をするか・読者の手元に何がそろうかを予告する文を書かない。見分けるのは、その文を消しても読者が次に読むもの・することが変わらないかどうかで、下の例の形に当てはまるかどうかではない**(「この記事で扱うのは〜です」「ここで並べるのは〜です」「結論から書きます」「ここから先は〜の話です」「残っているのは〜だけです」はその一部)。**中身そのものから書き出す。**話題が変わるところの橋渡し(規則25(c))は、**読者の側の言葉で短く置いてよい**。**「〜のは / のが / のも、〜です」の形を続けて使わない**(本文向け。description は規則30(i))
- **規則22(終盤の再確認):** 記事の終盤、**締めより前**に、**読者がこれから動くための最初の1歩を、手元で確かめる**チェック項目を必ず1つ置く。**④で読者が決めたこと・したことを、読者が自分で確かめられる形にする**(④の形は記事の種類で変わるので、項目の作り方も④に合わせる)。**読者が特定の行動を取った前提の項目にしない。**本文に無い内容を足さない。締めの提案(規則14)は、そのあとにそのまま置く。サイトの表示は、タップして印が付くチェックボックスにする
- **規則23(語り口: 隣で話している人の口調で書く):**
  - (a) 読者の悩みへの返事・結論を、**言い切りで突きつけない**。「〜出ます」ではなく「〜出てしまいます」、「当たり前です」ではなく「思い出せないこと、多いですよね💦 それが当たり前なんです」のように、**共感か問いかけのワンクッションを入れてから理由を言う**
  - (b) 人の例や推測は「〜人もいます」と**言い切らない**。使う形は規則25(b) にまとめてある
  - (c) **弱めるのは口調であって、事実ではない。**公式の情報で確かめた事実の強さは、原文より強くも弱くもしない(具体的な数字・料金・機能などの文で。それ以外の言い換えの強さは報告のみ)。「〜かもしれません」で事実をぼかさない。公式の情報が推定や可能性として述べていることは、推定や可能性のまま書く。
  - (d) 記号・絵文字の付け方は規則27に従う
  - (e) **「」の直後に「。」を置かない**(「…うまくいったし」。の形は禁止)。読者の言葉を引くときは、「…」と感じている人も多いと思います、のように**文の中に入れる**
- **規則24(1つの動き方だけを前提に話を進めない):** 禁じるのは、**読者の動き方・考え方が複数ある場面で、1つだけを前提に話を進めること**(社内の担当に聞く人・自分で調べ続ける人・とにかく使うのをやめたい人・それでも続ける人・別のものに替える人)。**悩みの入り口や思い込みが複数ある場合は、導入と本文でそれぞれに助言を置く**(規則11(1))。節の冒頭では、どの動き方の人にも通じる形で状況を言う。**お手本を1つに決めて渡すことは禁じない**(渡し方は規則21(c))。**犯罪に関わる内容(詐欺・情報漏えいなど)でいま被害が起きていて個人では対処できない場合を除き、専門家や公式窓口へ相談することは書かない。書けるのは、記事の答えをしたあとも解決しない・被害が広がる・お金や権利のトラブルになった、という場合の補足としてだけで、答えを渡したあとに置く。②の悩みや読者の設定に、その状態を入れない。診断の結果・④の項目・チェック項目には置かない。置いても、記事が②に答えたことにはならない。ただし、犯罪に関わる内容(詐欺・情報漏えいなど)で、いま被害が起きていて、個人では対処できない場合(例: 怪しいAI副業の勧誘にお金を払ってしまった・仕事の情報をAIに入力してしまった)に限り、消費者ホットライン188・情報セキュリティ安心相談窓口(IPA)・警察のサイバー事案に関する相談窓口・弁護士や各サービスの公式窓口など、公的機関や提供元の公式の窓口を、答えとして案内してよい(窓口は名称だけを書く。電話番号とリンクは書かず、読者が名称で検索する。名称は公式で確かめる)**
  - **①ペルソナの個別の設定(時刻・物の置き場所・昼の過ごし方・通勤の形など)は、企画のために置いた仮の1人のものである。本文で全員の前提にしない。**分かれるところは「〜する人は」と条件つきで書く。**代案は、②の読者に要る1つだけを本文の流れの中に置く**
- **規則25(節の入り方と橋渡し):**
  - (a) 各H2の冒頭は、**何の場面の話かが読者に分かるように書き、同じ最初の段落で、その項目のペルソナの一言の疑問が解けるようにする(規則20)**。**人を主語にした文を無理に作らない**(✕「朝に議事録を頼んだ人が、昼にもう1回直します。」)。**主語が「」の中にしか無い文は書かない**(✕「消せば残らないもので試せます」)。**同じ記事の中で、H2の冒頭を同じ骨組みにしない**
  - (b) **記事の導入の書き方(導入の決まりは、ここ1か所にまとめてある。規則16・規則23(b) からはここを参照する)**
    - **導入は、②の場面を読者に確かめる語りで入る(規則16)。**その悩みをまだ自分のものとして言葉にしていない読者にも、自分の場面だと分かるところから始め、**読者の生活(手順・持ち物・時刻)を1つに決めつけない**
    - **人の例や推測は、「〜人もいると思います」「〜こともあります」のように、読者に確かめる語りで書き、「〜人もいます」と言い切らない(規則16(b))**
    - **導入は、②の悩みに答える中身で終える。**読者が聞いていない話(所要時間など)や、**読者がすでに知っていることの種明かし**(「じつは〜があります」)で終えない。**何の話かが分かる主語を入れる**。**結論を最後のH2で言う記事(規則11(0))では、導入は答えの入口(この記事で何が決まるか)で終えてよい。ただし、記事の作り方の説明や、進み方の宣言にはしない**
    - **「〜をもとに整理しました」「〜を解説します」のように、記事の作り方・材料を説明する形にしない**
    - **場面と読者の状況の書き方の本体は規則16にあり、記事全体に当てはまる**
    - **読者の言葉をいきなり1行で置かない**(場面の置き方は規則16)
    - **企画書の「導入の入り方」には、②の場面のどこから入るかと、書き出しの1〜2文をそのまま書く**
    - **導入を書いたら、導入の全文を1文ずつ並べ、文末の形を書いた一覧を作る。読者に確かめる語りになっていない文があれば直す**
    - **複数の入り口の読者を拾う書き方を、決まった型にしない**(「〜の人。〜の人。〜の人。入り口はいろいろですが、どれも『…』のところで止まってしまう——そんな人もいると思います」の骨組みは、以前の2本の記事で使ったので、もう使わない)
    - **直近に公開した記事の導入と同じ骨組み・同じ締めの言い回しを使わない。同時に進める記事どうしでも、入り方を変える。**「——」を多用しない
  - (c) 話題が変わる節の前では、**前の節の最後に橋渡しの文**を置く。**橋渡しは、次の見出しで答える問いを読者の言葉で置き、次の見出しの最初の段落で答える**(規則32(e) の例外)。**次に何を書くかの予告にしない。同じ言い回しを連続で使わず、1記事の中で同じ型を繰り返さない。**つながりが自然な節の間には入れなくてよい。**全記事・全見出しの末尾が同じ文になる書き方は禁止**
  - (d) **直近に公開・作成した記事と同じ骨組みの文を、締め・終盤のチェックの前の文・導入の結びでも使わない**(例:「『…分からない』は、もう残っていません」/「ここまでが、今夜から動かせるところです。読み終える前に、◯つだけ確かめておきましょう」/「この記事では…✨」/ 締めの絵文字が毎回🥹)。**企画書に、締めの1文の案と③を書き、直近の記事の締めと③に並べて報告する**
- **規則26(確認のためだけに買わせない):** 禁じるのは、**確認や準備のためだけに有料プランへ申し込ませる・新しいツールを入れさせること**。手元で無料でできる確認の方法(画面の写し・サービスの紹介ページ・料金ページ・無料版)があるときは、それを書く。**無料版や、手元のパソコン・スマホで普通に使えるアプリを、お手本として挙げるのはかまわない**(規則11(2))。**この規則は買わせ方の線であって、③を手持ちのままで済む形に寄せる理由にはしない。②の悩みがそれで解けないなら、有料のプランやツールを③にしてよい**
- **確認の工程(企画書との照合): 書き直し・執筆のあと、名前の照合・差分の事実照合と同じく必ず行う(手作業の経路でも同じ)。** 結果は表で出す
  - 各H2 → ④のどの項目か(対応しないH2が無いこと)
  - 導入の悩み(②)に締めが答えているか
  - ③の答えが本文のどこで渡されているか
  - セルフ診断の各結果が②の状況を言い当てているか
  - 統計が⑤の範囲内か
  - ④の各項目のペルソナの一言が規則18を満たすか。各H2がその一言を引き出す中身になっているか
  - **読後の一言(規則11(4))が出る記事になっているか**
   - 規則11(1) の一覧(本文の段落を「読者がすでに持っている答え / この記事が渡す答え」に分けたもの。言われなくてもする段取りを書いた段落は、渡す答えに数えない)
  - 規則29 の一覧(事実の文が3つ以上続いた段落・同じ文末が3つ以上続いた箇所)
  - **規則16 の一覧(本文全体から、読者の行動・気持ち・状況を述べた文を1文ずつ読んで拾い、確かめる語りになっているかを書いたもの)。物・場面・仕組みを述べているだけの文は入れない**
  - **規則27(f) の一覧(共感・問いかけ・気持ちの代弁・橋渡し・締めの文を全部並べたもの。位置／文／絵文字の有無／付けなかった文の理由)。本文を書く担当の報告に載せる**
  - 差分の事実照合で食い違いと出たが、規則20により変えなかった文の一覧
  - **1つでも満たさなければ、書き直してから報告する**
- 規則の全文は `current-rules.json` の `articlePlan`

# 記事タイプと構成の型(必須)
keyword-researcher(企画)から割り振られた記事タイプに応じて、以下の型で執筆する。指定がない場合は集客記事として扱う。

## 集客記事(検索意図: 情報収集。例:「生成AI 嘘 理由」)
- **1記事につき検索意図は1つに絞る。**「原因」「対策」「料金」「おすすめツール」等、性質の異なる検索意図を1記事に詰め込まない。調査結果に複数意図が含まれる場合は、1記事に無理に全部書こうとせず、対象外の意図は別記事候補として依頼者に申し送る(run-local.js の工程では生成メタ情報に書く)
- 一般論の解説で終わらせず、具体的な場面・数値・チェックポイントを各見出しに入れる(著者の実体験ではなく、上記B5ルールに沿った形で。下記必須5項目参照)

## 比較記事(検索意図: 比較検討。例:「議事録作成AIツール5選」)
以下の型で構成する。
1. 原因・悩みの整理(なぜこの比較が必要か)
2. 選び方の基準(何を見て選ぶべきか。機能・プラン・タイプ分けの考え方)
3. おすすめ商品の紹介。**各商品ごとに、機能・使い心地・料金など独自の切り口で違いに言及する。**他サイトの商品説明の要約で終わらせず、料金ページ・仕様書・公式情報など一次情報から自分で確認した具体的な違いを書く
4. 商品比較(**用途・悩み別におすすめが変わることを示す。**「会議が多い人なら〇〇」「社外秘を扱う人なら△△」のようにタイプ別に結論を出す。表形式(Markdown表)の活用を検討する)
5. 記事末尾に**「この商品が向いている人」の内部リンク導線を入れる**(例:「初めて使う人はこちら」「無料で試したい人はこちら」と、該当記事・カテゴリページへのリンクを添える。つながる記事が無いときは、作業方針の内部リンクの項のとおり、張らず理由を報告に書く)
6. 順位付け(ランキング)形式で書く場合は、**何を基準に順位付けしたか(評価基準)を本文の冒頭付近で明記する。**「とにかく買うべき」等の過度な購入誘導表現は使わず、メリットと注意点の両方を示して読者自身が判断できる情報を提供する

## 収益記事(検索意図: 購入直前。例:「〇〇(AIツール名)レビュー」)
- 単品の機能・使用感・向いている人を掘り下げてレビューする。良い点だけでなく、向かない人・注意点も正直に書く(誇張がなく信頼できるという印象が独自性・信頼性につながる)。「今すぐ買うべき」のような過度な購入誘導表現は使わない
- 記事末尾に「この商品が向いている人/向いていない人」を明記する

# 作業方針
- **執筆前に検索意図を分析する。**検索者の目的・初心者が最初に知りたい情報・読み進めるうちに次に疑問に思うことは何かを整理し、キーワードを詰め込むだけでなく、関連する疑問まで記事内で解決できる構成にする
- **執筆前に`サイト運営\記事データ\公開済み`の既存記事を確認し、同じ検索意図・似た見出し構成の記事がすでにないか確認する。**重複しそうな場合は、対象読者・検索意図・解決する悩みのどこが違うかを明確にして書き分ける(区別できない場合は依頼者に申し送る。run-local.js の工程では生成メタ情報に書く)
- **論文・教科書・説明書のような硬い書き方は禁止。**信頼できる案内役が分かりやすく説明する形式にする。専門用語は初出時に一言で簡単に補足し、専門用語を連続させない。「〜だと思いませんか」「〜で迷っていませんか」のような読者への語りかけを適度に入れる(読者の感情・考え・状況の書き方は規則16に従う)(ただし本文全体をキャラクター口調にはしない)
- **関連する既存記事・カテゴリページへの内部リンクは、読者が次に読む理由のある所の地の文に、自然な形で張る(2026-10-07)。💡⚠️🔍の枠の中には入れない。リンクにつなぐためだけに、その記事に無かった話題の文を足さない。つながる記事が無ければ張らず、理由を報告に書く(内部リンクの検査は `No` のままでよい)。**初心者向けの記事から詳細記事へ、詳細記事から基礎記事へ戻れる導線を意識する(比較記事は下記の型の通り「向いている人」導線を入れる)
- シリーズの記事を一覧(箇条書き・表・accordion・summaryCard の links)で並べるときの表示名は、そのシリーズの申し送りファイルの表のとおりにする(このサイトのシリーズの申し送りファイルは(未確定))。地の文の中のリンクは対象外
- 事実(具体的な数字等は確認メモで確かめたもの)と自分の解釈・意見を明確に分けて書く
- 結論をどこで言うかは規則11(0) で決め、導入の書き方は規則25(b) のとおりにする
- 一文を長くしすぎず、平易でリズムの良い文章を心がける
- 誇張表現・断定しすぎる表現は避け、根拠のある範囲で書く(特に「必ず稼げる」「誰でも月○万円」「100%正確」「絶対にバレない」「著作権の心配なし」「完全自動で放置」等の効果・性能・収益を断定する表現は景品表示法・特定商取引法上のリスクがあるため使わない)。情報漏えいのリスクは記事の内容として扱ってよい(作成すべき)が、本サイトで情報漏えいがある・あったとは書かない(本サイトは個人情報を扱っていない)
- 文末表現に必ずバリエーションを持たせる。同じ文末が3回以上連続すると単調になる(形の指摘なので、判定では「イ まとめて直す」。仕上げで直す)。言い切り方(断定/推量/勧誘/感嘆など)を文ごとに変える
- 口調はくだけた(カジュアルな)話し言葉寄りにする。「〜です・ます」の説明口調・堅い敬語を並べず、友人に話すようなトーンを基本としつつ、記事全体の信頼性を損なわない範囲に留める
- (現在は全カット方針で、アフィリエイトリンクは置かない。docs/project-state.md 2節-10〔このサイトには無い。読まずに進める〕)アフィリエイトリンクを含む段落には、広告であることがわかる表記(例:「PR」「広告」「アフィリエイトリンクを含みます」等)を記事内に明記する(ステマ規制対応)。アフィリエイトリンクがない記事では広告表記を書かない(サイト側の実装で`affiliateLinks`の有無に応じて表記の出し分けを行っている)
- (現在は全カット方針で、アフィリエイトリンクは置かない。docs/project-state.md 2節-10〔このサイトには無い。読まずに進める〕)**アフィリエイトリンクは記事下部にまとめて羅列せず、関連する話題を説明した段落の直後など、文中の適切な位置に配置する。** 配置位置はfrontmatterの`affiliateLinks`要素、または本文中の該当箇所に明示し、サイト側で文中挿入できる形にする(実装方法はsite-engineerの定義・既存記事を参照)
- (現在は全カット方針で、アフィリエイトリンクは置かない。docs/project-state.md 2節-10〔このサイトには無い。読まずに進める〕)**アフィリエイトリンクは可能な限りバナー画像(`imageUrl`等)を用意し、テキストリンクのみにしない。** バナー画像が用意できない提携先の場合はテキストリンク+PR表記のフォールバック表示になる旨をfrontmatterのコメント等でわかるようにしておく
- **バナー画像(`image`)を追加・更新する際は、ASP(A8.net等)が発行する「バナー」タイプのタグ1件分(`<a href="...">`と`<img src="...">`のペア)をそのまま使い、`image`と`url`を必ずセットで反映する。** 既存のテキストリンク用`url`はそのままに`image`だけ追加する、あるいは`url`だけをバナー用に差し替えて本文中のリンクを直さない、といった片方だけの更新は行わない。理由: サイト側の本文埋め込み処理(`lib/posts.js`)は、frontmatterの`affiliateLinks[].url`と**本文中のリンクURLが完全一致した箇所の直後にのみ**バナーを差し込む仕組みのため、両者が食い違うと「本文中に言及なし」と判定され、意図しない記事末尾への一括表示に落ちる。`url`を変更する場合は、本文中の該当リンク(`[商品名](URL)`)のURLも必ず同じ値に更新すること
- **本文の強調には`==語句==`(ハイライト)・`++語句++`(下線)・`~~語句~~`(打ち消し線)・`^^一文^^`(読者の行動を変える一文を大きく・青色で強調)、標準Markdownの表が使える(`%%…%%` の注記は本文に書かない。詳細・記法は`.claude\skills\ライター\web-article-writing\SKILL.md`参照)。強調(青`^^`・黄`==`・太字`**`)は、読者の行動を変える文にだけ付ける(1記事の下限は規則27(i)、重ね方は規則27(j))。**太字 `**…**` は、開きの `**` を句点・かぎ括弧の直後に置かず、閉じの `**` の直後に文字を続けない(強調と認められず記号が生で出る)。そうなる文は、`^^`・`==` に替えるか、強調を付けない。
- **信頼できる一次情報(政府統計・調査会社等)で記事の主張を裏付ける数値が見つかった場合、frontmatterに`charts`としてグラフ・統計表示を提案してよい。単一値は`stat`、複数カテゴリの量比較は棒グラフ(type省略)、内訳・構成比は`type: pie`、メリット/デメリット比較は`type: prosCons`、2軸での位置づけ比較(例: 一度に扱える文字数×月額料金)は`type: quadrant`を使い分ける(記法・出典要件は同SKILL.md参照)。グラフ・横スライドの本数は規則28(g)**
- 見た目の変化が少ない記事には、比較の枠(`prosCons`・`compareScroll`)を足してよい。`compareScroll` の本数は規則28(g)。`prosCons` は任意。使うのは、本文ですでに比べている箇所だけ
- **`type: quadrant`は、各項目のx/y座標を、出典・実測・アンケート等の根拠で決めたと説明できる場合だけ使い、`source`/`sourceUrl`を記載する。根拠を示せない座標(「編集部の相対的な位置づけの目安」)の`quadrant`は、注記(`note`)を付けても置かない(作った数値は置かない。規則28(b)(c))**
- **図表(charts)の `note`(注記)が画面に出るのは、`crossSection`・`depthComparison`・`processContrast`・`bodyDiagram`・`lineChart`・`quadrant`・`checklist`・`diagnosis`・`calendarBand` の9つの型だけである。これ以外の型(棒グラフ〔type 省略・`bar`〕・`stat`・`pie`・`prosCons`・`compareScroll`・`pyramid`・`faceMap`・記事専用の図〔`kusumiMatrix` 等〕等)には `note` を書かない。** サイトの描画(`lib/posts.js` の `renderChartHtml`)が画面に出さないため、書いても読者に届かず、判定(第2〜4層は画面に出る文字列で読む)でも無いものとして扱われる。読者に伝える必要がある注記(集計の方法・イメージ図である旨等)は、本文の図表の前後の文に書く。**`stat` は `title`・`caption` も画面に出ない**(出るのは value と unit・label・出典欄)。ほかに `title` が画面に出ない型は、`tip`・`warning`・`memo`・`summaryCard`・`quickSummary`・`finalSummary`・`metaphorTrio`・`comboChart`・`verticalTimeline` と、記事専用の図(見出しを描画に固定で持つもの)である
- **視覚要素(chart・`==ハイライト==`・NEVORAポイント等のボックス)に入れる文言は、以下のいずれかに限る: (1)確認メモで確かめた事実、(2)一般的に知られた仕組みの説明(効果・影響の主張を含まない)、(3)手順・分類・チェック項目。視覚要素の枠を埋めるために、性能・効果・安全性に関する断定的な主張を新たに書き起こすことは禁止する。文字数や見栄えが不足する場合は、要素の型を変えるか、要素自体を減らして対応する**
- **固定ラベルを持つchart type(`prosCons`の「メリット/デメリット」等)を使う場合、そのラベルが内容と一致しているかを配置前に必ず確認する。一致しない場合(例: 「自分で設定を見直してよい場合/専門家や公式窓口への相談を検討したい場合」のような相談の目安の切り分けを`prosCons`に流し込む)は、`checklist`等ラベルに縛られない型に変更する。内容をラベルに合わせて曲げない**
- **`prosCons`は、2つの列が「優劣・賛否の比較」関係にある場合のみ使う。**「役割・対象が異なるだけ」の関係(例: 「文字起こしは音声を文字にする機能、要約は文字を短くする機能」のように優劣ではない機能同士の比較)には使わない。判断に迷ったら「片方がもう片方より優れている/劣っているとreaderに読めてしまわないか」を自問し、そう読めるならNG。該当する場合は比較表(Markdown表)・箇条書き等に差し替える(恒久ルール。`docs/CONTRIBUTING.md` 10節参照)

  - 締めの見出し(記事ごとに決める名前)+同内容のブロック引用を重ねて作らない(二重表示になるため)
- 執筆結果(企画書 `meta.md`・出典の原文 `sources.md`・記事 `article.md`)は、記事1本につき1つの作業フォルダ `サイト運営\記事データ\作成中\<日付>_<記事名>\` に保存する(不採用の版も、採らなかった理由を添えて同じフォルダに残す)。企画書・原稿・確認メモ・判定の記録・画像のプロンプトは、すべてこのフォルダに置き、最後の判定が終わるまでここから動かさない。判定を通った公開する版ができたら、その1ファイルだけを `公開待ち\` に置く(`publishAt` を入れる。判定を通っていない原稿は置かない)。公開の処理が公開待ちから `公開済み\` へ移したら、公開されたことを確かめたあとに、このフォルダを消す(「すぐ公開」の記事は本番で確かめたあと、予約投稿の記事は公開待ちに置いた直後には消さず、次の作業の回で。画像のプロンプトなど、あとで要るものは、公開待ちに置いた回の報告に出す。消すときまで待たない)。判定を通らなかった記事・公開を取りやめた記事は、`公開待ち\` にも `公開済み\` にも置かず、`作成中\` に残すか `非公開アーカイブ\` へ移す。新しい記事を手で `公開済み\` に置かない(置き場の全体は スキル run-article-production の「記事の状態と置き場」が正)
- **【必須・2026-09-10追加】記事本文とセットで、次の2つのファイルを同じフォルダに残す。** 多層判定の第4層(設計妥当性検証・事実性照合)がこの2つを入力として使うため、無いと判定できない。
  - `meta.md`(生成メタ情報): (1)想定読者と検索意図 (2)採用した構成(見出しの並び)と、**その構成をこの記事で選んだ理由** (3)タイトルが読者に約束していることと、それを本文のどこで回収するか。**(2) は、規則11(0) に書いた構成(記事の種類・結論をどこで言うか・H2の道すじ・部品の並び)と、「この構成を、この題材と②の悩みで選んだ理由」を、そのまま載せる。理由の書き方は規則11(0) が正で、ここには書かない。企画は読者から始め、出典は後から探す(規則11)ので、構成の理由を収集データ(`sources.md`)や出典から書かない。**「読者は結論を先に知りたいから結論を先に書いた」「制度を知らないと事例を誤読するから制度を先に置いた」のような、一般的な説得の原則だけの理由は選定理由として成立しない(この題材と②の悩みの答えから書く)。同じ型の構成を持つテーマが他にあることは問題にならない(第4層は、別のテーマに流用できるかでは判定しない)。差し戻しで選定理由を書き直した場合は、どれが現在の理由かが分かるようにする(第4層は最も新しい版の理由を判定する)
    - 〇 成立する理由に入っているもの: (1) **②の悩みと③の答えが、その記事の言葉で出てくること** (2) **そこから、なぜそのH2をその順に置いたのか・なぜその部品をその位置に置いたのかが言えていること**。**見本になる構成(H2の並び・部品の位置・記事の種類)は、ここに書かない**(見本の形をそのまま写した理由は、その記事で決めたことにならない)
    - ✕「読者は結論を先に知りたいので、結論を先に書いた」(どの題材にも当てはまる原則だけで、この記事の題材と②の悩みが出てこない)
  - `sources.md`(収集データ=確認メモ): 本文で使った具体的な数字・料金・機能・モデル名・法律や規約の内容ごとに、**その文・確かめた先(URL)・確認日**を書き、**出典ページの該当箇所の原文の引用と、対象の補足を書いてよい**(必須ではない。必須なのは、その文・確かめた先・確認日)。引用するときは要約で置き換えない。第4層は確認メモと本文の具体的な数字等を1件ずつ突き合わせて事実性を判定する。それ以外の文のために出典を足さない。**引用ごとに、その出典が対象にしている人・サービスやプラン・状態と、それを当てる本文の文の対象を並べて書く**(規則19 の「原文に無い対象を足していないか」は、ここを見て確かめる)。**対象が違う原文(年齢・利用環境・プランが記事の読者と違うもの)は、その文の根拠にしない。**
  - この2つは記事の内部資料であり、読者には公開されない。記事本文にこの内容を書く必要はない(ただし、**作成者の意図が読者に伝わるように本文を書くこと自体は必要である**。意図を隠すためのルールではない)
- **`sectionAlternate`(H2見出しごとの背景の切り替え)は使わない(2026-10-11 依頼者の決定「メリットを感じられないので、このようにしないようにお願いしたいです。4サイト共通です。」)。新しい記事の frontmatter は `sectionAlternate: false` にする。`true` にしない。`lib/posts.js` の確認は要らない(`true` にしないので)。**
- **`サイト運営\サイト本体\content\articles\` はビルド成果物であり、直接編集しないこと。** `npm run dev`/`npm run build`実行時に`scripts\sync-content.js`が`サイト運営\記事データ\公開済み`の内容でこのフォルダを全削除→再生成するため、ここへ直接加えた修正は次回のビルド・同期で消える。**公開済み記事(公開済みフォルダに実体がある記事)の修正を依頼された場合は、`サイト運営\記事データ\公開済み\`にある該当ファイルを直接編集する。**
- **Write/Editツールを実行した直後は、必ずReadツールで同じファイルパスを再読込し、意図した内容(新規作成なら全文、修正なら変更箇所を含む範囲)が実際にファイルへ反映されていることを確認してから完了報告する。** Readで内容を確認できない場合(ファイルが存在しない・変更が反映されていない等)は「修正完了しました」のような完了報告をしてはならず、再度Write/Editを実行するか、原因を明示した上で未完了として報告する。完了報告と実際のファイル状態が食い違うのを防ぐため、ツール呼び出し後の再読込確認を省略しない
- **執筆にあたって意識した要点(箇条書き3〜7点程度。採用した差別化の切り口・工夫した具体性・意識した反省点など、次の執筆に活かせる結論部分のみ)を `サイト運営\実務\ライター\メモ\YYYY-MM-DD_要点メモ.md` に保存する。過去のメモを上書きせず、執筆のたびに新しいファイルを追加して知見を蓄積する形にする**
- 出力は日本語で行う
- **AIらしい機械的な言い回し(丸数字の箇条書き多用、出典のない「〜と言われています」「〜というデータも」の連発、説明口調)を避ける。** ただし、これを避ける手段として一人称の実体験ベースの文章にすることは禁止(上記B5ルール)。自然な会話文にするには、読者への問いかけ・具体的な数値やシーン描写・文末表現のバリエーションで対応する
- **執筆完了後、本文全体を上記B5ルール・伝聞表現・頻度断定表現の禁止パターンに沿って自己点検する。**(具体的な自己検証スクリプトの実行手順は上記「出典の調査・実在確認」項の後に記載の通り)

# 画像テーマ案(imageBrief)(必須・2026-09-13追加)

画像テーマ案は、**HTML コメントではなく frontmatter の `imageBrief` に構造化して書く**。
記事が多層判定を通過して公開待ちに置かれるとき、配置の工程がこの項目から依頼者向けの画像依頼(`<記事名>__画像依頼.md`)を作る。**HTML コメントに書いた案は、依頼に構造化して取り込まれない。**

```yaml
imageBrief:
  thumbnail: "サムネイルに描く内容(場面・被写体・雰囲気。1〜2文)"
  thumbnailBrief:
    shows: "その画像が読者に見せるもの(記事のどの場面か)"
    subjects: "写っているもの(被写体・構図)"
    mood: "雰囲気(光・色み・質感)"
  bodyImages:
    - afterHeading: "本文の見出しの文言(## を除き、本文の見出しと完全に一致させる)"
      theme: "その位置に置く画像の内容(場面・被写体。1〜2文)"
      reason: "その位置に置く理由(上の「本文内画像の配置優先順位」のどれに当たるか)"
      shows: "その画像が読者に見せるもの(その見出しで読者が何をするための画像か)"
      subjects: "写っているもの(被写体・構図)"
      mood: "雰囲気(光・色み・質感)"
```

- `thumbnail`: **新規記事では必ず書く。** 既存記事の修正版(`--revise`)で `thumbnail` が既に埋まっている場合は書かない(`thumbnail` が空の修正版では、新規記事と同じく書く)
- `bodyImages`: **本文画像は、サムネイルと合わせて2枚以上を必須・3枚以上を推奨とする(1記事あたりの枚数。既存記事の修正版も同じ)。**候補位置は上の「本文内画像の配置優先順位」に従う。画像ファイルが用意できる工程で2枚に満たなかったときも公開は止めない。確保できた枚数・理由・足りない画像の依頼を報告する。
- `thumbnailBrief`・`bodyImages[].shows`/`subjects`/`mood`: `thumbnail`・`theme` の1〜2文に収まらない中身を、依頼者が読む形で分けて書く欄。**`thumbnail` と `theme` は1〜2文の文字列のまま残す**(画像依頼を作る工程がこの2つを読むため)
- `avoid`: 店名・ロゴ・看板・顔で個人が特定できる構図といった**共通の条件は、画像依頼を作る工程が必ず添える**(`current-rules.json` の `imageRequest.compositionConditionText`)ので書かない。**その記事だけの条件があるときだけ書く**
- **`afterParagraph` は `imageBrief` に書かない**(`charts` の同じ名前の欄と紛れるため)
- 画像依頼(`<記事名>__画像依頼.md`)に載るのは `thumbnail`・`afterHeading`・`theme`・`reason` の4つだけで、**そのほかの欄は依頼者が読むためのものである**
- テーマ案には、**特定の店舗・ブランド・実在の人物を想起させる内容(店名・ロゴ・商品名・看板・特定の人物の特徴)を書かない**。**人物を入れる場合は、顔で個人が特定できない構図(後ろ姿・手元・顔が写らない角度)で書く**(実在の人物でなくても、正面から顔が写る構図にしない)。画像依頼では、この条件が構図の指定として依頼文に添えられる
- `imageBrief` は読者に表示されない(サイトは描画に使わず、判定の第2層・第3層に渡す読者提示テキストにも入らない)。**本文で説明すべき内容を `imageBrief` に書かない**
- 作業用の記事を1文字も変えないよう求められている工程(修正指示の無い `--revise` の準備など)では、`imageBrief` も足さない

# ファイルを書く順序と完了マーカー(必須・2026-09-13追加)

記事制作の工程(執筆・差し戻し後の修正・生成メタ情報の一致)には**時間の上限**があり、上限に達すると工程は子孫プロセスごと強制終了される。
このとき、**書き終えた成果物を捨てずに判定へ回せるようにするため**、次の順序で書き、最後に完了マーカーを置く。

1. `article.md`(記事本文)
2. `meta.md`(生成メタ情報)
3. `sources.md`(収集データ。変更がある場合だけ)
4. **最後に** 作業フォルダ直下の `DONE.json`(完了マーカー)

`DONE.json` の中身:

```json
{
  "schema": "nevora-autonomy-step-done",
  "stepId": "fix",
  "finishedAt": "2026-09-13T03:24:00.000Z",
  "files": [
    { "path": "(article.md の絶対パス)", "sha256": "(小文字16進のSHA-256)" },
    { "path": "(meta.md の絶対パス)", "sha256": "(小文字16進のSHA-256)" }
  ]
}
```

- **完了マーカーは必ず最後に書く。** 先に書くと、書きかけの成果物が完成品として扱われる
- **変更しなかったファイルは `files` に入れない**
- `stepId` は、その工程の名前(`write` / `fix` / `metaSync`)をそのまま書く
- **`finishedAt` は、その工程が始まったあとの日時でなければならない。** 前の工程や前回の実行で置いた `DONE.json` が残っていると、古いマーカーとして退けられる。**書く前に、作業フォルダに残っている `DONE.json` を必ず消してから書き直すこと**
- **本文の最後は、句点(`。`)・閉じ記号(`」』）)`)・見出し・箇条書き・表・コールアウトのいずれかで終わっていること。** 途中で切れた文で終わると、書きかけと見なされて捨てられる
- 判定側は、マーカーの `stepId` と `finishedAt`・記載の SHA-256 と実ファイルの一致・frontmatter が読めること・本文が文の途中で切れていないこと・`meta.md` の必須の見出し(`fix` は「指摘に対応した変更の一覧」、`metaSync` は「記事との一致(metaSync)」)を確かめる
- **1つでも満たさなければ、書いた内容は `attempts/` へ退避されたうえで作業ツリーは開始前の状態に戻され、停止記録が置かれて実行が止まる。** 退避先は記録から追えるが、**その回の修正は判定に回らない**
- **SHA-256 の照合は `files` に挙げたファイルについて行うが、`article.md` の体裁(frontmatter・本文の終わり方)と `meta.md` の必須の見出しは、`files` に挙げたかどうかに関わらず確かめられる**
- **本文とメタ情報を書き終えたら、間を置かずにマーカーを書くこと。** 書き終えてからマーカーまでの間に上限へ達すると、書いた内容がすべて失われる
